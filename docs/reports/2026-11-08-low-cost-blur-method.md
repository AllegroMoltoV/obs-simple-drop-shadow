# 大半径の影を低負荷で描画する方式の比較

確認日: 2026-11-08

## はじめに

ぼかし半径の上限を 1024 にする要求に向け、ピクセルシェーダーだけで大半径のぼかしを低負荷に描画する方式を比較しました。調査には imozuru スキルを使いました。原文・抜き書き・詳細レポートは、ローカルの `~/research/realtime-large-blur/` にあります。原文は再配布できないため、リポジトリには置きません。

- `map.md`: 論点ごとの原文の場所
- `report.html`: 原文の抜き書き 28 件。原文との一致を機械で照合済み
- `digest.html`: 水準別の解説と検索の全記録

## 背景

現在のエフェクトは、横方向と縦方向の 2 パスに分けたボックスブラーです。1 画素当たりの読み取りは `4r + 2` 回で、半径 1024 では 4,098 回になります。経緯は `docs/reports/2026-11-08-ui-improvement-survey.md` にあります。

## 検証方法

英語の用語検索と、定番の講演や OBS プラグインの実装を探す検索を、別々の検索役に担当させました。挙がった原典・解説・OBS プラグインのソースを保存し、該当する行を確認しました。OpenGL 変換の制約は、手元の OBS 31.1.1 のソースで確認しました。

## 検証結果

### 方式ごとの計算量と測定

| 方式 | 1 画素当たりの読み取り | 半径への依存 | 出典 |
| --- | --- | --- | --- |
| 現行の分離型ボックス | `4r + 2` 回 | 比例 | 本リポジトリの実装 |
| 線形補間の分離型ガウシアン | N タップ当たり約 N/2 回 | 比例 | Rákos 2010 |
| 縮小してからぼかす | 縮小率の 2 乗で画素数が減る | 比例。ただし係数が小さい | Strugar 2014 |
| Kawase blur | 1 パス 4 回、パス数は半径に対して線形未満 | 線形未満 | Strugar 2014 |
| Dual filtering (Dual Kawase) | 縮小 1 段 5 回、拡大 1 段 8 回。段ごとに画素数が 1/4 | 段数が対数で増える | Bjørge 2015 |
| 移動平均ボックス | 半径に依存しない | なし。ただし計算シェーダーが必要 | Strugar 2014 |

測定値は次のとおりです。

- Bjørge 2015 では、Mali-T760 で 97x97 相当のぼかしを比べ、Dual filtering が最速でした。総帯域は、線形補間ガウシアンの 7% でした。
- Strugar 2014 では、R9-290X で 127x127 のガウシアンが約 3ms、1/2 縮小で 0.5ms、1/4 縮小で 0.17ms でした。Kawase blur は、最適化したガウシアンの 1/1.5 から 1/3 の時間でした。
- Rákos 2010 では、線形補間により、離散サンプリングより約 60% 速くなりました。
- デスクトップ GPU で 1080p・半径 1024 相当を測った数字は見つかりませんでした。

### 画質

- ボックスは重みが等しいため、ぼかしの形がブロック状になります (Bjørge 2015)。
- 単純なミップマップ生成による縮小は、ブロック状の劣化と、動いたときの不安定さを示しました (Bjørge 2015)。
- 縮小して戻す方式では、ぼかしが小さいとブロック状の模様が目立ちます (Strugar 2014)。小さい半径では縮小しない画像と補間する対策が示されています。
- Dual Kawase は、同じ縮小段数でもちらつきが出ないと説明されています (FrostKiwi 2025)。拡大の段を飛ばすと、格子状の劣化が出ます。

### OBS プラグインの実装

- obs-composite-blur と StreamFX は、Dual Kawase を段数で制御しています。StreamFX の段数の上限は 16 です。
- obs-composite-blur は、2 のべき乗の段の中間の強さを、1 段多く処理した結果との混合で作っています。
- obs-shaderfilter は、辺ごとの拡張画素を設定値で受け取り、`get_width` と `get_height` で拡張後の大きさを返しています。

### OBS の描画 API

- OBS 31.1.1 の OpenGL 変換は、`Sample`・`SampleLevel`・`Load` を GLSL の関数へ置き換えます (`libobs-opengl/gl-shaderparser.c` 425-436 行)。
- `gs_timer_create`・`gs_timer_begin`・`gs_timer_end`・`gs_timer_get_data` で GPU 時間を測れます (`libobs/graphics/graphics.h` 644-784 行)。
- 1 チャネルの描画先として `GS_R8` と `GS_A8` があります (`libobs/graphics/graphics.h` 58-59 行)。

## 考察

### 推奨する方式

Dual Kawase を推奨します。根拠は次の 3 点です。

- 段数が半径に対して対数で増えるため、半径 1024 でも 1 画素当たりの読み取りがほぼ一定になると考えています。縮小 1 段ごとに画素数が 1/4 になるので、全段の合計は最初の段の 4/3 倍程度に収まると推測します。
- 動いたときのちらつきが出にくいことが示されています。配信の映像は常に動くため、この性質が最も重要だと考えています。
- OBS のプラグイン 2 つで実績があり、使う構文は `Sample` だけなので、OpenGL 変換の制約に当たらないと考えています。

ほかの方式を採らない理由は次のとおりです。

- 線形補間ガウシアンと縮小の組み合わせは、計算量が半径に比例したままです。半径 1024 では縮小を重ねる必要があり、結局 Dual Kawase に近い構成になると考えています。
- 移動平均ボックスと SAT は、計算シェーダーか高精度の中間テクスチャを必要とするため、OBS のエフェクトでは実装の負担が大きいと考えています。

### 実装上の論点

- 影に要るのはアルファ値だけです。中間テクスチャを `GS_R8` などの 1 チャネルにすれば、帯域を RGBA の 1/4 にできると推測します。8 ビットで段を重ねたときの階調の劣化は、実装時に確認が必要です。
- 半径を連続的に変えるには、段の中間を補う必要があります。obs-composite-blur の混合と、StreamFX のサンプル距離の調整の 2 つの方法があります。
- 小さい半径では、縮小によるブロック状の劣化が出ると考えています。半径が小さい範囲だけ現行の分離型ボックスを残す案と、縮小しない画像と補間する案を、実装時に比べる必要があります。
- 現行のボックスと Dual Kawase では、同じ半径でも影の見た目が変わります。既存利用者の影の見た目が 0.2.0 で変わる点は、更新情報に書く必要があると考えています。
- 性能は、既存のテスト基盤で `gs_timer` を使い、D3D11 の GPU 時間を測る方法が適していると考えています。Strugar 2014 と同じく、影なしで描画した時間との差を取ります。
